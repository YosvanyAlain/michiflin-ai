# Session access control

`OWNER_ADDRESS` identifies the owner. An optional, separately configured `OWNER_BACKUP_ADDRESS` is also an administrator; without it the owner remains the sole administrator. The production environment starts with `OWNER_ONLY=1`, so only those explicitly configured administrators are admitted initially. `MAINTENANCE_MODE=1` takes precedence, restricts service access to administrators and cannot be disabled from the mini app. The separate operational-maintenance notice pauses work and resumes eligible queues afterward. Neither an old allow-list entry nor an old job grants access.

The default verified-contact mode requires the owner's pinned key and verified guest contacts. Separately opted-in email-key recovery weakens this protection: a currently permitted address may bind a new encrypted key without proving the old one. A sender impersonating that address may thereby obtain its privileges, even though the messages are encrypted. After a new binding is checkpointed, an earlier key is retired; old backups are not deleted. Old chat-bound jobs and WebXDC local storage remain preserved but are not automatically transferred to the replacement chat. No address gains access merely from a historical or expired grant.

The owner can use **Administration → Approve one person** to authorize exactly one named contact and open a temporary session in a single confirmed action. The owner can also use **Administration → Access control · OWNER_ONLY** to request an in-memory opening for 15 minutes, 1 hour, 4 hours, 24 hours, or until restart. Opening requires confirmation and **does not authorize anyone automatically**: approve each address explicitly in the same screen. Closing or revoking blocks new work and pauses pending guest work without deleting historical data. A message already handed to the mail core just before closure may still complete.

`/owner_only` reports the effective mode, `/owner_only 1` closes it, and `/owner_only 0 15` requests a 15-minute opening. The confirmation code is single-use and expires in five minutes. Use `/admin_allow` and `/admin_remove` for specific addresses. Never share the code or the owner's session. These owner controls remain available during the kill switch; maintenance cannot be opened.

Overrides and guests exist **only in memory**. On restart, the configured `OWNER_ONLY` value and its prior boot policy apply; a configured `1` returns to owner-only. The app refreshes after expiry, subject to asynchronous email delays. Old guest jobs and WebXDC instances cannot resume on reauthorization; the guest needs a new app. If the mail core cannot unblock a contact, authorization fails closed. In the default verified-contact policy, a guest must also complete SecureJoin; an address grant alone does not verify their key. The separately opted-in email-key recovery policy deliberately relaxes this identity check for currently authorized addresses. An identity cutover with strict epoch keeps previous jobs stored but does not send or resume their old chat/message IDs.
