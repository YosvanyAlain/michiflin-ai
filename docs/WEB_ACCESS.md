# Web search and Live browser

## Interactive web sessions

**Web** provides internet search and a field to paste an HTTPS address into an interactive isolated browser. HTTPS search results also have an **Open in Live** action, while the title still opens the lightweight reader. The account owner may enter their own login and must complete any verification; no website-specific API registration is needed for Live. It works only in a supported Delta Chat client with the experimental WebXDC realtime channel and in an authorized individual encrypted chat. Frames and typed input go over that ephemeral channel, not WebXDC status updates; the server processes them and delivery may fail or be delayed. A phone was observed opening public pages in earlier disposable staging; that does not establish compatibility with every client or an authenticated social login.

Choose the browser mode before starting. **Graphical with session** uses visible Chromium on the server, operated with the person's gestures. Playwright restores compatible saved state on start, saves cookies and site data only when requested, and obtains the current page address for supported downloads; its control uses a private pipe rather than a TCP debugging port. **Temporary graphical** launches Chromium directly without WebDriver, CDP, page scripts, or an automated CAPTCHA solver; it neither loads nor changes existing saved sessions, and save and private-video download are unavailable. Both modes use the same public-HTTPS gateway and OS isolation, with temporary profiles and clipboards in the isolated session's tmpfs; there is no fallback to a less isolated browser. The host needs full Playwright Chromium, Xvfb, xdotool and xclip. Some earlier apps supported a former headless mode; with this deployment's current-only gate they no longer operate the bot. Disabling browser infobars may hide additional warnings; the external jail remains essential and must not be bypassed. Synthetic sessions passed save/restore and isolation checks, and one small anonymous public Wikimedia video was downloaded locally. No personal login, private-video access or CAPTCHA acceptance was established. Sites can still detect or reject either mode.

**Less data** is the initial mode, using a 480×760 frame and lower JPEG quality. **Sharper** can use up to 960×1520 pixels while taps still address a 480×760 coordinate space (the full browser window in both graphical modes; older headless clients used the page viewport). Very complex frames automatically fall back to 480×760 to fit the channel. Switch to sharper if a verification image is hard to read, understanding that it may use more data. The first frame opens in a compact workspace with history, page reload, view refresh, page-scroll arrows, the picture and the text field together. **Fit** shows the entire image; the nearby **Zoom** control cycles through 150%, 200% and Fit. Magnification is local to the displayed image: with Swipe and Drag off, pan it to see hidden portions; the arrows scroll the remote page. At very small sizes the fitted image can be hard to read, so use Zoom and pan. Further gestures, save, capture, address and quality controls are below the workspace. Still-frame refresh every five seconds is opt-in and uses data; it is not video streaming.

Tap the remote field, type in Live's labelled field and choose **Send text**; Enter in this local field also sends the text, while the separate **Enter** button sends that key to the remote page. An overlong text or a locally rejected oversized payload stays in the field so it can be shortened. A response lost after an operation is different: do not blindly repeat an unconfirmed action. Tab, Enter, Backspace, visibility and Zoom controls are beside the field; other keys remain below. If a status notice is too long for its space, scroll inside it to read it in full. The layout adapts to the visible viewport where the client exposes it, but physical Android/iOS keyboards and every WebXDC host have not been tested. The remote picture is a raster image, not an accessible semantic web page; local controls have names and keyboard focus, but this does not establish screen-reader access to the remote site or its challenges.

If Google or another service says this browser is unsafe, **Open initial address in the device browser** offers an ordinary HTTPS link in a new window; the WebXDC client decides whether and how to open it. It opens the initial address, not the current remote page, and never copies cookies or a login back to Live. There is no claim that Google will accept the remote browser or that this link supplies an official OAuth integration. Google's [OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies) prohibits developer-controlled embedded user agents for OAuth authorization; that policy must not be generalized into proof about every kind of Google login. No personal Google login was tested. Follow the provider's verification and security requirements rather than disguising the browser or bypassing checks.

For challenges or other controls needing a hold or drag, turn on **Hold or drag**, perform the gesture yourself on the image, and then turn it off to resume tapping or panning the enlarged image. One recorded pointer path, at most 8 seconds and 64 samples, is sent over the same ordered channel; retries cannot execute the same gesture twice. This does not analyze, solve, evade or guarantee acceptance of any CAPTCHA. Additional keys include Space, Esc, Shift+Tab and left/right arrows. Real provider behavior, mobile gesture support and accessibility features such as audio challenges remain unverified. The Live app's address field accepts a direct address for the same service; provider-driven redirects and sign-in pop-ups may visit other domains. In graphical mode the app refuses to paste an address while a pop-up window has focus, because that window may not have an editable address bar. Complete the pop-up or use **Close current window** first; closing the last window ends the browser and discards unsaved changes, while previously saved state remains. The browser's own address bar and links can visit other sites within the same temporary profile. For a different service, close the browser and open a separate session.

Live displays a per-session estimate of app payload bytes sent and received, including repeated packets. It excludes QUIC/retransmission overhead, mail, background traffic and any billing classification: it is neither a complete data-usage meter nor an ETECSA balance. Frames and input continue to use the ephemeral realtime channel, not mail or persistent status updates. A Nauta account being included in Plan toDus does **not** prove the separate realtime P2P/relay connection is included; it may consume other data or fail. The actual plan charged must be checked on the user's line with a small deliberate test, without promises of realtime over email.

A current app in an authorized encrypted chat receives a specific message when the kill switch is on. In this deployment `MINIAPP_CURRENT_ONLY=1` rejects every earlier build, even a formerly compatible one. An old instance may receive a best-effort retirement hint on new activity, but delivery is not guaranteed. To obtain the current app, explicitly send `/app` in the authorized, encrypted private chat; a current app may also offer an explicit request under **Settings → Synchronization**. Each app has independent local storage: older messages and data are not deleted or automatically migrated. Revoked, foreign, unencrypted and group-chat instances remain rejected without sensitive responses.

When no realtime reply arrives, the current app distinguishes a channel that never answered from a browser that answered but did not produce a frame. Neither message by itself proves why the failure occurred: the bot may be offline, the peer connection may be unavailable, or another condition may have intervened. A session is limited to 300 seconds of inactivity or 20 minutes total, with an aligned worker deadline; on expiry the bot makes a best-effort realtime close notification. Provider deadlines, host restarts or delivery failures can still end it earlier. Delivery over this experimental channel is not guaranteed.

Some web-index results have video actions. A download attempt uses that person's saved browser state for the service if available, or public access otherwise; search results can be incomplete and neither a recognized link nor a queued job proves a download succeeded.

Choose **Save session** explicitly and confirm it to encrypt the browser state for that person and the initial site of this Live session. Cancel or dismiss the confirmation to leave the stored copy unchanged. The confirmation belongs to the open Live session: if that session ends or changes during the prompt, review the site and confirm again. The server accepts worker state for persistence only as the response to the explicit save action, and reports a vault error rather than a successful save when encryption or writing fails. The state may contain bearer-equivalent cookies, local storage and IndexedDB, including data from third-party sign-in domains visited within that browser, so it is as sensitive as a credential. It is encrypted under the separate stable `WEB_SESSION_KEY`, in `CONFIG_DIR/browser-sessions-v1`, with distinct keys and filenames for each person and site; backups encrypt the state again. A key change or loss makes old sessions unavailable. Saving does not prove login succeeded, and providers can expire or reject sessions. A normal browser on the phone has separate storage; its sessions are not transferred to the bot.

**Send screenshot to chat** deliberately creates a persistent attachment in the encrypted chat. Both current graphical modes capture the visible browser window. Earlier headless clients could capture up to 3,000 CSS pixels starting at the scroll position, but cannot operate when current-only is enabled. The attachment and backups can outlive the browser session. **Download this video**, available in the savable mode, queues a supported video from the current page using the same person's saved cookies and user-agent, subject to normal download settings and limits. Close other tabs and windows first: if several pages are open, the graphical mode refuses the download rather than picking the wrong page. It does not forward local storage or IndexedDB to yt-dlp; websites that require those mechanisms may fail. Private/unlisted URLs are kept in server-side job metadata, which is included in encrypted state backups, but not in realtime acknowledgments or WebXDC status updates. Only download content that you own or have permission to download.

**Forget session** closes active browsers for that person/site and deletes the current encrypted file. It does not revoke the provider's session or erase older encrypted backups; sign out/revoke at the provider to invalidate it. Production must provide Linux namespaces, sudo, chroot, socat, iproute2, util-linux, a Playwright Chromium installation, yt-dlp and ffmpeg. Without isolation or `WEB_SESSION_KEY`, the browser fails closed. Isolated browser and private-media workers have no external network route except through the host gateway; they do not inherit the bot's environment or home directory. The ordinary page/file client, headless browser, and public-media yt-dlp clients also use short-lived loopback proxies backed by this gateway rather than making an unpinned connection themselves; Chromium's implicit loopback proxy bypass is disabled. For every HTTP or HTTPS hop, the host resolves the destination, rejects mixed or non-public answers, and connects to a vetted numeric address; redirects are checked hop by hop. HTTPS remains end-to-end with the original hostname for SNI and certificate validation. CGNAT and IPv4-mapped private addresses are treated as non-public. Local synthetic regression tests cover rebinding to loopback, numeric connections, streaming response cleanup, and the HTTP/HTTPS proxy paths; they do not contact external sites.

The browser was tested with a demonstration login, including encrypted save and restore, and media with a protected **local test fixture**. In disposable staging a mobile client displayed public pages, while Facebook presented challenges and Google rejected a software-controlled login. A public web index found TikTok results and one separately selected public TikTok video was downloaded locally, with its advertised permission not independently verified. These observations do not prove social account login, private YouTube downloads, an authenticated Facebook capture, MFA, or native TikTok search. Google may refuse controlled browsers; providers can require CAPTCHA, block automation, change pages, or prohibit the requested access. Complete challenges yourself; do not bypass them or promise universal access.

A proxy or Cloudflare WARP can change the network path but is neither a browser nor proof of trust; it may increase challenges or invalidate sessions. Live's Chromium and isolated private-media worker use the sandbox's local gateway. The gateway routes **both Live and its isolated private-media worker** through the nonempty `WEB_PROXY`, or `MEDIA_PROXY` if `WEB_PROXY` is empty; if neither is set, it connects directly. SOCKS5 (`socks5` or `socks5h`) and HTTP CONNECT upstreams are supported. Host-side page/file requests, the headless browser, and public yt-dlp operations use a short-lived loopback proxy backed by the same destination checks; ordinary HTTP is forwarded only after resolving and pinning its public numeric address. The worker never receives the upstream address or its credentials. Every requested destination is resolved on the host, all answers must be public, and the gateway sends a vetted **numeric IP** to the upstream: even `socks5h` does not delegate target DNS resolution. TLS to the website remains end-to-end with the original host name. The code-execution sandbox receives no new network access.

Calls to fixed provider APIs (model discovery, image generation, translation, search, GitHub, the update check, linked accounts) do not accept redirects: a 3xx answer is refused instead of replayed against the new location, because Requests only strips `Authorization` across hosts and would still forward API keys sent in other headers or in the query string. Requests to open, credential-free endpoints that may legitimately redirect — news and encyclopedia indexes, geocoding and forecast, MDN, Stack Overflow, GitHub code search, the bandwidth probe, and the maintenance/backup scripts that download release assets — keep following redirects to their own fixed hosts; they carry no user-controlled destination. Page, file, media and browser traffic, where the destination does come from a person, always goes through the pinning gateway.

The production workflow exports `MEDIA_PROXY=socks5://127.0.0.1:40000` only after its WARP trace reports `warp=on`; if WARP was not verified and no other proxy is configured, Live starts directly and says so. If a configured proxy is unreachable or becomes unavailable, Live reports an error and **does not silently retry direct**. The indicator says only whether a proxy is configured; it does not prove WARP is on. To check the current browser path, open `https://www.cloudflare.com/cdn-cgi/trace` as a separate site in Live and look for `warp=on`. This intentionally displays the current public IP to the account holder; do not share it unnecessarily. DNS validation still uses the runner's resolver, and other bot features need not use the same proxy. Separate connections or runner jobs can have different public IPs. No IP rotation or alternate-route/client retry is attempted after a recognized verification challenge, and geographic IP spoofing in the ordinary downloader is disabled.

`YTDLP_COOKIES` remains a single administrator-only facility for the public-link downloader, not a per-person session; never place other people's cookies there. The Downloads tab is independent of any account-connection screen.

## Previously stored sessions and API tokens

No new account-connection screens are offered in this version. The YouTube video and audio downloader is separate and remains available under its existing conditions. This interface change does not delete existing browser sessions or API tokens, revoke provider permissions, or erase backups. Earlier app messages retain their local storage, although they cannot operate with the bot when current-only is enabled.

Browser sessions and previously saved API tokens are stored separately per person and site, encrypted using `WEB_SESSION_KEY`, and may also exist in encrypted backups. Losing or rotating that key makes existing data unreadable. To forget a browser session, open that site in Live and use **Forget session**; that does not revoke the session at the provider or erase historical backups. Removing a screen alone does not disconnect or revoke anything.

Named sites may be entered manually, but provider rules and technical blocks still apply; login and restoration have not been verified for every service. Do not interpret an API connection, saved state, or displayed login form as proof of successful website login. Do not paste passwords, cookies, refresh tokens or access tokens into chat or search fields, and do not bypass CAPTCHA.
