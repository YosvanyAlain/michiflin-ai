# Web search and Live browser

## Interactive web sessions

**Web** provides internet search and a field to paste an HTTPS address into the interactive, isolated Playwright-controlled Chromium browser. HTTPS search results also have an **Open in Live** action, while the title still opens the lightweight reader. The current miniapp no longer shows preset site cards or the previous official account-connection cards. The account owner may enter their own login and must complete any verification; no website-specific API registration is needed for Live. It works only in a supported Delta Chat client with the experimental WebXDC realtime channel and in an authorized individual encrypted chat. Frames and typed input go over that ephemeral channel, not WebXDC status updates; the server processes them in memory and delivery may fail or be delayed. A phone was observed opening public pages in disposable staging; that does not establish compatibility with every client or an authenticated social login.

**Sharper** frames use up to 960×1520 pixels while taps still address a 480×760 CSS viewport. Very complex frames automatically fall back to 480×760 to fit the channel; **Less data** uses that smaller size from the start. Magnification is local to the displayed image: pan it to see hidden portions, and use the arrows above the view to scroll the remote page. The first frame is brought into view automatically. Still-frame refresh every five seconds is opt-in and uses data; it is not video streaming. The address bar accepts a direct address for the same service; provider-driven redirects and sign-in pop-ups may visit other domains. For a different service, close the browser and open a separate session.

A current app in the authorized encrypted chat receives a specific message when the kill switch is on. An older app is not allowed to open a browser: the bot sends a fixed denial and, at most once per 30 minutes per chat, an explanatory message in that private chat. Older app builds may show a generic error because they do not recognize the new code; open the latest app from the chat, or use **Settings → Sync now** to request an update. Existing app instances and their local data are not deleted. Neither the denial nor the explanatory chat message contains the visited address, frames, input or session data. Revoked, foreign, unencrypted and group-chat instances remain rejected without a response.

When no realtime reply arrives, the current app distinguishes a channel that never answered from a browser that answered but did not produce a frame. Neither message by itself proves why the failure occurred: the bot may be offline, the peer connection may be unavailable, or another condition may have intervened. A session is limited to 150 seconds of inactivity or 10 minutes total; on expiry the bot makes a best-effort realtime close notification. Delivery over this experimental channel is not guaranteed.

Some web-index results have video actions. A download attempt uses that person's saved browser state for the service if available, or public access otherwise; search results can be incomplete and neither a recognized link nor a queued job proves a download succeeded.

Choose **Save session** explicitly to encrypt the browser state for that person and site. The state may contain bearer-equivalent cookies, local storage and IndexedDB, including data from third-party sign-in domains visited within that browser, so it is as sensitive as a credential. It is encrypted under the separate stable `WEB_SESSION_KEY`, in `CONFIG_DIR/browser-sessions-v1`, with distinct keys and filenames for each person and site; backups encrypt the state again. A key change or loss makes old sessions unavailable. Saving does not prove login succeeded, and providers can expire or reject sessions. A normal browser on the phone has separate storage; its sessions are not transferred to the bot.

**Send screenshot to chat** deliberately creates a persistent attachment in the encrypted chat, up to 3,000 CSS pixels starting at the current scroll position; the attachment and backups can outlive the browser session. **Download this video** queues a supported video from the current page using the same person's saved cookies and user-agent, and sends the result subject to normal download settings and limits. It does not forward local storage or IndexedDB to yt-dlp; websites that require those mechanisms may fail. Private/unlisted URLs are kept in server-side job metadata, which is included in encrypted state backups, but are not included in the realtime acknowledgment or WebXDC status updates. Only download content that you own or have permission to download.

**Forget session** closes active browsers for that person/site and deletes the current encrypted file. It does not revoke the provider's session or erase older encrypted backups; sign out/revoke at the provider to invalidate it. Production must provide Linux namespaces, sudo, chroot, socat, iproute2, util-linux, a Playwright Chromium installation, yt-dlp and ffmpeg. Without isolation or `WEB_SESSION_KEY`, the browser fails closed. Browser and media workers use an HTTPS gateway which blocks private-address destinations; they do not inherit the bot's environment or home directory.

The browser was tested with a demonstration login, including encrypted save and restore, and media with a protected **local test fixture**. In disposable staging a mobile client displayed public pages, while Facebook presented challenges and Google rejected a software-controlled login. A public web index found TikTok results and one separately selected public TikTok video was downloaded locally, with its advertised permission not independently verified. These observations do not prove social account login, private YouTube downloads, an authenticated Facebook capture, MFA, or native TikTok search. Google may refuse controlled browsers; providers can require CAPTCHA, block automation, change pages, or prohibit the requested access. Complete challenges yourself; do not bypass them or promise universal access.

A proxy or Cloudflare WARP can change the network path but is neither a browser nor proof of trust; it may increase challenges or invalidate sessions. Live's Chromium uses the sandbox's local HTTP CONNECT gateway. The gateway routes **both Live and its isolated private-media worker** through the nonempty `WEB_PROXY`, or `MEDIA_PROXY` if `WEB_PROXY` is empty; if neither is set, it connects directly. SOCKS5 (`socks5` or `socks5h`) and HTTP CONNECT upstreams are supported. The worker never receives the upstream address or its credentials. Every requested destination is resolved on the host, all answers must be public, and the gateway sends a vetted **numeric IP** to the upstream: even `socks5h` does not delegate target DNS resolution. TLS to the website remains end-to-end. The code-execution sandbox receives no new network access.

The production workflow exports `MEDIA_PROXY=socks5://127.0.0.1:40000` only after its WARP trace reports `warp=on`; if WARP was not verified and no other proxy is configured, Live starts directly and says so. If a configured proxy is unreachable or becomes unavailable, Live reports an error and **does not silently retry direct**. The indicator says only whether a proxy is configured; it does not prove WARP is on. To check the current browser path, open `https://www.cloudflare.com/cdn-cgi/trace` as a separate site in Live and look for `warp=on`. This intentionally displays the current public IP to the account holder; do not share it unnecessarily. DNS validation still uses the runner's resolver, and other bot features need not use the same proxy. Separate connections or runner jobs can have different public IPs. No IP rotation or alternate-route/client retry is attempted after a recognized verification challenge, and geographic IP spoofing in the ordinary downloader is disabled.

`YTDLP_COOKIES` remains a single administrator-only facility for the older public-link downloader, not a per-person session; never place other people's cookies there. The Downloads tab is independent of the removed platform cards.

## Previous account connections and stored sessions

The current miniapp no longer presents platform-specific shortcuts or the previous YouTube, Facebook and TikTok API connection screens. This interface change **does not delete saved browser sessions or API tokens, revoke provider permissions, alter the server's existing operations, or erase backups**. Previously delivered app messages retain their old appearance; open the newest miniapp from the private chat. Older builds are not allowed to perform normal operations against the current backend.

Browser sessions and older API tokens are stored separately per person and site, encrypted using `WEB_SESSION_KEY`, and may also exist in encrypted backups. Losing or rotating that key makes existing data unreadable. To forget a browser session, open that site in Live and use **Forget session**; that does not revoke the session at the provider or erase historical backups. For a previously authorized official account connection, revoke the app directly in the provider's account permissions if it is no longer wanted. Removing a card alone does not disconnect anything.

Named sites may be entered manually, but provider rules and technical blocks still apply; login and restoration have not been verified for every service. Do not interpret an API connection, saved state, or displayed login form as proof of successful website login. Do not paste passwords, cookies, refresh tokens or access tokens into chat or search fields, and do not bypass CAPTCHA.
