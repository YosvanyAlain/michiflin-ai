# Encrypted state backups and technical maintenance

## Storage and recovery

`state_backup.py` defaults to `STATE_BACKUP_STORAGE=releases`: each encrypted archive is a separate asset of a **private** GitHub release, not a new Git commit. A fresh salt and Fernet key derived from `STATE_BACKUP_PASSPHRASE` encrypt each archive. Never publish the passphrase, the GitHub token, or a decrypted archive. `STATE_GITHUB_TOKEN` must have Contents read/write on the private backup repository. The workflow still saves every 30 minutes and at shutdown.

The backup is downloaded independently, compared to the upload, decrypted, extracted into temporary storage, and its SQLite databases checked before it is marked usable. The first save creates an application-owned, state-free release anchor and a ready marker; neither is the default branch. After that marker exists, a missing release cannot silently fall back to a stale Git snapshot. In the clean-owner namespace, recovery refuses automatic fallback when the newest snapshot is invalid; in other namespaces it can try older marked snapshots. Recovering an older copy can lose newer work or delivery reservations, so verify current state before any manual recovery. Network errors fail closed. Existing local state is never overwritten.

The new workflow sets `STATE_BACKUP_RETAIN_ALL=1`, so it does not automatically rotate snapshots or stale pending assets. This setting does not change an already-running older session: until it stops, that session can still rotate after verifying two separate snapshots. Its ordinary policy keeps six recent snapshots, representatives of five days and three ISO weeks, plus the oldest clean-owner seed (categories overlap). Unknown assets are not touched by that rotation. A local lock serializes saves on the same runner, not other runners or an external rename. Storage and release asset capacity are finite; a failed new save leaves earlier copies intact but means the latest changes might not have been backed up. Do not delete backups to solve capacity problems without a separate decision.

On the first deployment only, if the release and ready marker do not exist, restore can migrate from an existing encrypted Git snapshot. The private `main` may contain a frozen, stale legacy snapshot or, after a separately authorized retirement, only a state-free anchor; inspect it rather than assuming the old account is recoverable. **Do not delete the reserved release or tags or switch to `legacy-git` as a routine rollback.** Before reverting to old software, first use the current release-aware code to restore the newest verified snapshot to a safe local directory. Merely restarting old code can restore stale state.

Backups are **not a complete archive of every attachment or work file**. The workflow includes attachment blobs in general but excludes files classified as audio or video within them, as well as `.tmp` files. The temporary queue and workspace outside `CONFIG_DIR` are not part of the snapshot. Completed downloaded media may be removed locally under the existing runtime setting; separate exports must be verified. The encrypted release snapshot is rejected above 256,000,000 bytes and prior copies remain. If the final backup fails, automatic session handover is stopped; an ephemeral runner cannot guarantee preservation of work since the previous successful snapshot.

Removing reachable refs or release assets does not guarantee immediate physical erasure from GitHub's caches, retained objects, clones, or external copies. GitHub controls garbage collection. The private repository and release must remain private and the encryption passphrase must be preserved separately.

## Diagnostic log cleanup

The daily `Technical maintenance` workflow removes **only GitHub Actions log files** older than 30 days, after preserving the latest ten completed runs per workflow, with at most 100 log sets per pass. It does not delete workflow runs, check results, artifacts, caches, contacts, messages, keys, or ambiguous user history. If it cannot obtain a complete run listing, it deletes nothing. GitHub's own retention policies still apply and may remove data sooner. Runtime diagnostic buffers are already bounded and reset between sessions.

A future explicitly requested one-time user purge may leave older verified recovery snapshots under the above retention schedule. Successful verification of a sanitized snapshot is **not** proof that all older copies, caches, remote mail, or external copies were immediately erased.

GitHub Actions remains a temporary host with policy and availability risks; this maintenance does not turn it into a guaranteed permanent server or a complete disaster-recovery service.
